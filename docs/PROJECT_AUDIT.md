## 2. Existing architecture

```
Browser / Electron window ──HTTP──► Express (server.ts, 0.0.0.0:3000)
                                     ├─ /api/*  (73 routes, JWT + role middleware)
                                     ├─ Vite dev middleware (NODE_ENV != production)
                                     └─ static dist/ + SPA fallback (production)
                                     │
                                     ▼
                         sql.js in-memory DB ──export()──► data/khushi_pharmacy.sqlite
                         (path = process.cwd()/data)        (tmp file + rename)
```

- **Single process, single thread.** sql.js is synchronous, so requests never interleave inside a handler. That gives accidental serialisation, but no crash durability between `saveDatabase()` calls.
- **Multi-tenant ("multi-store") SaaS model.** The `tenants` table and a `tenant_id` column on most tables scope data per store. SUPER_ADMIN supervises every tenant and can impersonate one ("login-as").
- **Frontend** is one SPA with tab state in `App.tsx`. Tabs are mounted lazily and kept alive. All HTTP goes through `request()` in `src/lib/api.ts` with `API_BASE='/api'` (relative URL), except one direct `fetch('/api/backup/mysql-export')` in `SettingsBackupScreen.tsx:44`.

## 4. Database structure

There are 17 tables, created by `CREATE TABLE IF NOT EXISTS` in `initDatabase()` (`server.ts:68-281`) and then extended by about 20 `ALTER TABLE … ADD COLUMN` statements wrapped in `try {} catch {}` (`server.ts:284-302`).

| Table | Key columns / constraints | Notes |
|---|---|---|
| `users` | `username UNIQUE`, `role`, `status`, `tenant_id`, `customer_id`, `allowed_services` | An old `CHECK(role IN …)` variant is rebuilt by an ad-hoc migration (`server.ts:332-357`) |
| `tenants` | `owner_email UNIQUE`, `status`, `plan`, `max_users`, `max_products`, `allowed_services` | Tenant #1 is force-created as "Khushi Medical Hall" |
| `categories` | `name UNIQUE` (**global, not per tenant**) | Two stores cannot both have "Tablets" |
| `suppliers` | n/a | n/a |
| `products` | `stock INTEGER`, **single** `batch_number`, **single** `expiry_date`, `purchase_price`, `sale_price`, `barcode`, `gst_rate`, `min_stock` | **Medicine-level stock only** (see §10) |
| `customers` | `phone UNIQUE` (**global**), `current_balance`, `login_id UNIQUE` | n/a |
| `customer_ledger` | `type CHECK IN (SALE, PAYMENT, ADJUSTMENT)`, `balance_after`, `sale_id` | n/a |
| `sales_headers` | `invoice_number UNIQUE`, `payment_method CHECK IN (CASH, PARTIAL, UDHAR)`, `payment_status CHECK` | n/a |
| `sale_items` | `product_id`, `quantity`, `batch_number`, `cost_price` | n/a |
| `purchase_headers` / `purchase_items` | `invoice_number UNIQUE` | n/a |
| `stock_adjustments` | `adjustment_type CHECK IN (ADD, REMOVE)`, free-text `reason` | n/a |
| `email_queue` / `sms_queue` | `type CHECK`, `status CHECK` | n/a |
| `settings` | `key PRIMARY KEY` (**global**, despite a `tenant_id` column) | Tenants share one settings namespace |
| `audit_logs` | `ip_address`, `user_agent`, `tenant_id` | n/a |
| `otp_verifications` | n/a | n/a |

**Foreign keys.** These relationships are declared:
- `products → categories, suppliers`
- `customer_ledger → customers`
- `sales_headers → customers, users`
- `sale_items → sales_headers, products`
- `purchase_headers → suppliers`
- `purchase_items → purchase_headers, products`
- `stock_adjustments → products, users`
- `email_queue/sms_queue → customers`

sql.js defaults to `foreign_keys = OFF`, so **none are enforced today**. Known code paths that create orphans:

| Path | Orphan created |
|---|---|
| `POST /api/settings/test-smtp` (`server.ts:2745`) | Inserts `email_queue.customer_id = 1`, whether or not customer 1 exists |
| `DELETE /api/customers/:id` | Must be checked for remaining ledger/sales rows (to be verified by `scripts/fk-audit` in Phase 3) |
| `DELETE /api/inventory/:id` | Leaves `sale_items` / `purchase_items` pointing at a missing product |
| `DELETE /api/superadmin/tenants/:id` | Tenant-scoped rows may remain |
| `tenant_id` columns | **Not declared** as FKs |

**Indexes.** Only the implicit ones from `UNIQUE` and `PRIMARY KEY`. There is no index on `products.barcode`, `products.name`, `sales_headers.sale_date`, `sale_items.sale_id`, `customer_ledger.customer_id` or any `tenant_id`.

**Migrations.** There is no versioning. Migrations are idempotent `ALTER … ADD COLUMN` statements whose errors are swallowed. **Every startup also runs data-mutating statements:**
- `UPDATE … SET tenant_id = 1 WHERE tenant_id IS NULL` on 9 tables.
- `UPDATE products SET barcode = '8901000000' || PRINTF('%03d', id) WHERE barcode IS NULL OR barcode = ''`, which **invents barcodes**.
- `UPDATE users SET full_name='Muhammad Asghar (Owner)', role='ADMIN' … WHERE username='admin'`, which **overwrites a customer's admin name on every start**.
- Super-admin enforcement (see §9).

**Sample database.** `data/khushi_pharmacy.sqlite.corrupt.1785024578279` is 123,414 bytes. Its header says 30 pages × 4096 = 122,880 bytes, so there are 534 unexplained extra bytes. A read-only `PRAGMA integrity_check` on a copy fails with **"database disk image is malformed"**. The likely cause is git text conversion or an interrupted whole-file rewrite; it cannot be proven. The file is kept untouched as evidence and will only ever be read through copies.

## 5. Authentication system

- **Login.** Username + password checked with bcrypt. An email OTP login also exists. Lockout uses an in-memory `loginAttemptsMap`.
- **JWT** signed with `process.env.JWT_SECRET || 'khushi_medical_hall_secret_key_2026'`. Because that fallback is **hardcoded and public**, anyone can forge tokens for any role. Expiry is 7 days for normal login and 24 hours for super-admin "login-as".
- **Middleware.** `authenticateToken` re-reads the user status and tenant suspension on every request, which is good. `requireRoles([...])` always lets SUPER_ADMIN through.
- **Roles.** `SUPER_ADMIN`, `ADMIN`, `STAFF`, `CUSTOMER`. Per-user `allowed_services` (CSV) drives sidebar visibility, but **only in the frontend**: backend routes check roles, not services.
- **Registration.** Customer and store self-registration use an email OTP. The OTP code is **returned in the HTTP response** (`server.ts:734` "for easy verification in UI demo mode"), which defeats the purpose of OTP.
- **Customer portal.** `CUSTOMER` users can only see their own data (`/api/customer-portal/me`, filtered `/api/sales/history`).

## 10. Reliability weaknesses (ranked)

| # | Severity | Finding |
|---|---|---|
| R1 | **Critical** | **Silent offline sales queue.** If `POST /api/sales` fails for *any* reason (including a 400 validation error or a 500), `BillingScreen.tsx:600-608` saves the sale to `localStorage`, **prints/downloads a receipt with an `OFFLINE-xxx` number as if paid**, and later re-posts it with **no idempotency**. A timeout after the server committed causes **double sales and double stock deduction**. |
| R2 | **Critical** | **No crash durability.** All data lives in memory; a power loss before `saveDatabase()` loses writes. Each save rewrites the whole DB (O(DB size) per write). |
| R3 | High | **Only `/api/sales` is transactional.** Purchases (header + N items + N stock updates), adjustments, customer payments, sale void, user/tenant deletes and restore are not, so a mid-way exception leaves partial state. |
| R4 | High | **Invoice numbers = `COUNT(*) + 1001` per tenant.** After any `DELETE /api/sales/:id` the next number collides with an existing one, the UNIQUE constraint fails, and **sales are blocked**. |
| R5 | High | **Overselling.** `stock = MAX(0, stock - qty)` silently records sales of stock that does not exist. |
| R6 | High | **Not batch-level.** `POST /api/purchases` **overwrites** `products.batch_number`, `expiry_date` and `purchase_price` with the newest purchase, so the expiry of older stock on the shelf is lost. Expiry alerts can be wrong. |
| R7 | High | **Hard delete of sales** (`DELETE /api/sales/:id`) removes financial records. The audit log keeps only a text line. |
| R8 | Medium | Startup mutations rewrite user data (admin name, invented barcodes) on every boot. |
| R9 | Medium | DB in `process.cwd()/data`, which in a packaged app is the install directory. Upgrades or uninstalls can lose data. |
| R10 | Medium | A corrupt DB at startup is renamed and **an empty DB is silently created with demo data and default logins**. The pharmacy would see an empty store, not an error. |
| R11 | Medium | "Daily auto-backup" does not back up. No retention, verification or history. |
| R12 | Medium | `navigator.onLine` is used as "server reachable". It reflects network-adapter state, not host availability. |
| R13 | Low | Unhandled errors in most routes. sql.js exceptions escape as 500s with stack messages, and there is no structured logging. |
| R14 | Low | `CURRENT_TIMESTAMP` is UTC while the UI shows local dates, so date-range reports can shift at midnight (to be verified with tests). |

## 11. LAN compatibility assessment

| Requirement | Today |
|---|---|
| Multiple PCs sharing one DB | Technically possible (server binds `0.0.0.0`), but **unsafe**: plain HTTP, open CORS, forgeable JWT |
| Single authoritative DB | Yes, one process owns it. Must remain the only access path; never share the `.sqlite` over SMB. |
| Concurrency | sql.js serialises requests. better-sqlite3 + WAL + `BEGIN IMMEDIATE` keeps that guarantee and adds durability. |
| Discovery / config | None. The URL is hardcoded to `localhost:3000`. |
| Change propagation | None. Other PCs only see changes after manual refresh or tab remount. |
| Disconnection behaviour | Dangerous (R1). |
| Verdict | **Not LAN-ready.** Needs HTTPS + pairing, an auth hardening pass, idempotent writes, real-time events and a connection-state UI. |

## 12. Required architectural changes

See `ARCHITECTURE.md`. In summary:
- Electron shell with a trusted `app://` UI and a pinned-HTTPS proxy in the main process.
- Backend in `utilityProcess`.
- better-sqlite3 behind a defined adapter, with a migration framework.
- Batch-level inventory with FEFO.
- Idempotent transactional writes.
- Authenticated SSE.
- Encrypted, verified backups.
- Configurable branding.
- NSIS and portable packaging built on GitHub Actions Windows runners.

## 13. Risks and proposed mitigations

| Risk | Mitigation |
|---|---|
| Data loss while migrating legacy DBs | Copy-only import, integrity check, verified pre-migration backup, per-migration transaction, row-count invariants, **stop and report** on any anomaly |
| Behaviour drift while replacing ~290 DB call sites | Characterisation tests written **before** the refactor; migration is done route group by route group |
| FK enforcement breaks existing data | Audit first (`scripts/fk-audit`), non-destructive fixes only with approval, then enable |
| Batch migration changes stock totals | One batch per product with stock > 0; invariant `SUM(batches) == products.stock` asserted |
| Native module (better-sqlite3) mismatch with the Electron ABI | `electron-builder install-app-deps` on the Windows runner; smoke test launches the installed EXE |
| Users locked out of LAN after certificate changes | Pairing flow, grace period on renewal, clear "re-pair" screen, documented procedure |
| Unsigned EXE → SmartScreen warnings | Signing hook ready (`CSC_LINK`); documented honestly |
| Hardware not testable in CI (printers, scanners, cameras, Wi-Fi) | Documented manual test scripts; marked "not executed" until performed |
| No real customer DB samples | Fixtures generated by running the **original** code; request anonymised real DBs from the owner |

## 15. Additional defects confirmed by the Phase 2 baseline tests

The executed baseline suite (`TESTING_REPORT.md`) confirmed the findings above and found more. The full table with the test that proves each one is in `TESTING_REPORT.md`.

- **First boot leaves every seeded row with `tenant_id NULL`.** The admin's audit log is empty, the demo sale is missing from the register, and other stores can see store #1 data until the app is restarted.
- **Deleting a product removes its lines from past invoices.** The invoice view uses an inner JOIN.
- **Deleting a customer erases their ledger** and writes no audit entry.
- **Deleting a store leaves orphaned child rows.**
- **Sales referencing a non-existent product are accepted.**
- **Customer portal logins are created with the default password `customer123`.**
- **An expired OTP stays valid until UTC midnight.**
- **The login-OTP endpoint reveals whether an account exists.**
- **CUSTOMER role can read cost prices** through `/api/inventory`.
- **Any store's ADMIN can clear every store's audit log.**
- **Overpayment makes customer balances negative.**
- **The original app injects its two SUPER_ADMIN accounts into an existing customer database during upgrade.**
